# The problem: equivalence is vacuous for M-cells

Measured, and pinned by `tests/toolchain/test_mcell_coverage.py`:

1. The front end emits a macro as a **dangling `(* gp_src *)` attribute**, not
   an instantiation, so `gatepack verify` on a macro design fails at C3 with
   `syntax error, unexpected TOK_ENDMODULE`.
2. Worse: with a netlist that *does* instantiate `CNT4`, a deliberately wrong
   model (`Q <= Q + 4'd2` instead of `+1`) is **not caught**. Equivalence reads
   `cells_sim.v` on both the golden and the gate side, so mutating the model
   changes both sides identically and Yosys still reports "Equivalence
   successfully proven!".

§19 R25 requires one shared model file so equivalence and simulation cannot
drift. That is satisfied — but only its trivial half. **Sharing the file is
precisely what makes the model uncheckable**: for a black box, the
specification side has no independent definition of the macro's behaviour, so
the model is compared with itself.

**M-cells ship in v0.1.0.** This has to be genuinely fixed, not deferred.

# Deliverable 2 — make a wrong model fail (the hard part)

The fix is an **independent** behavioural definition of each macro on the
specification side, derived from the design's own semantics rather than from
the file the netlist uses.

`gatepack/macros/models/CNT4.v` is the *implementation* model — what the mapped
netlist's `CNT4` cell means. What is missing is a *specification* model: what a
4-bit counter is required to do, written from the spec, against which the
implementation model is checked.

Approach is yours, but it must satisfy: **mutating `CNT4.v` makes the check
fail.** Weigh at least these:

- a spec-side behavioural model generated by C1 from the macro's declared
  semantics (period, enable, reset), which the golden side uses while the gate
  side keeps `cells_sim.v` — so the two are genuinely independent;
- a standalone macro-model equivalence check (`CNT4.v` versus the spec model)
  run once per macro, separate from the design-level equivalence;
- properties over the macro's behaviour discharged by sby, if that is a better
  fit than equivalence for a sequential macro.

Whatever you choose, **the mutation test is the acceptance criterion**:
`tests/toolchain/test_mcell_coverage.py::test_wrong_mcell_model_is_not_caught_by_equivalence`
currently asserts the *broken* behaviour to keep it visible. Invert it — it
must assert that the wrong model **is** caught — and it must fail if you revert
your fix.

Do not weaken the design-level equivalence to get there, and do not delete the
shared-file property R25 asks for: simulation and equivalence must still read
the same implementation model.
