## Verdict

The design is genuinely strong at the architecture level — the strategy boundary between sync/async (§7), verification-before-packing sequencing (§20), the mutation suite as an anti-vacuity guard (R2), and text-canonical/GUI-as-view (principle 2) are all correct and rare instincts. The single biggest risk is **provenance (§15.1)**: the entire linked-selection feature — the thing that "makes the application worth building" — is built on the false assumption that `src` attributes survive synthesis, and they do not survive `abc` or `dfflibmap`. Close behind it: the equivalence plan (§12/C4) as written will not close, and the async plan (§7.2) has three unstated showstoppers. The synchronous core is shippable; the async backend and the provenance spine are not.

## Critical issues

1. **§15.1 / §12 — `src` attributes do not survive `dfflibmap` or `abc`.** Yosys propagates user attributes through `proc`, `flatten`, `opt`, `fsm`, and `techmap` only partially; `dfflibmap` and `abc` replace the `$_*` cells with library-cell instances that carry no attributes, and `abc` renames cells arbitrarily. So the provenance map "source construct ↔ Yosys cell ↔ package refdes" has no spine on the *mapped* netlist — which is exactly what C12 renders and what M16's linked selection reads. The §15.1 honesty note ("many-to-many and lossy") understates this: the default state is *total* loss, not partial. **Fix:** capture provenance on the *pre-ABC* netlist (after `techmap`, before `dfflibmap`/`abc`), then carry it forward by cone-based reverse-matching against the post-ABC JSON (or by injecting a keyable string attribute into the pre-ABC cell names that you recover by matching connectivity). This is a first-class design item, not an assumption, and it must be prototyped before M16 is scheduled.

2. **§12 / §11 — `equiv_make`/`equiv_induct` will not close as specified.** You cannot `equiv_make` raw behavioural `generated.v` (with `always` blocks, enums, `$process`) against `mapped.json` (library cells). Equivalence requires both sides brought to a *common* abstraction: the golden must run through the same front-end passes (`proc; flatten; opt; fsm; opt; techmap; opt`) — but *not* `dfflibmap`/`abc` — before `equiv_make -seq`. Additionally, the golden's state encoding must match the mapped netlist's bit-for-bit for k-induction to prove, which only holds if `fsm` is run identically on both (see #3). A second, subtler bug in the same script: `setundef -zero` runs *after* `abc` in synthesis, so `mapped.json` has `x→0` while `generated.v` still carries `x` on don't-care inputs — `equiv` will spuriously disagree or require `-undef` handling on both sides. **Fix:** define a `golden_prep` script that mirrors C3's front end, run `equiv_make -seq` on the pre-`setundef` mapped netlist, or apply `setundef -zero` to *both* sides, and use `equiv_induct`/`equiv_status -assert` with a documented `-seq N`.

3. **§6.2 vs §12 — the default `fsm` pass re-encodes and defeats one-hot.** Yosys `fsm` (an alias for `fsm_detect; fsm_extract; fsm_opt; fsm_recode; fsm_map`) defaults to `-encoding auto`, which re-codes the state register (typically binary) using its own cost function. If C1 already emits one-hot encoding, running bare `fsm` will undo it — and even `fsm -encoding one-hot` is not guaranteed to match C1's hand encoding. The design's core trade ("flop output *is* the state signal") silently evaporates, and equivalence (#2) breaks because the encodings diverge. **Fix:** since C1 *is* the RTL generator and already chose one-hot, skip `fsm` entirely (or run `fsm -encoding one-hot` and verify the encoding is stable across a golden). Don't rely on bare `fsm`.

4. **§9.2 — factual errors in the F-cell / `dfflibmap` story.** (a) `-nodffe` is a `dfflegalize` flag, not a `dfflibmap` flag — and the C3 script doesn't run `dfflegalize` at all, which is the pass that actually converts an enable flop into a feedback mux. (b) "Anything absent gets synthesised out of gates on every flop's D input" is wrong: `dfflibmap` leaves an unmatched `$_DFF_PP0_`/`$_DFFE_*` *unmapped* (with a warning), and your own "no surviving `$_` cells" check then errors the build. The "reset becomes an AND on every D input" behaviour is what `dfflegalize -reset` (and enable-removal) does, not `dfflibmap`. (c) The `ff` group description is incomplete: `DFF_R` needs `clocked_on + next_state + clear`, `DFF_S` needs `preset`, `DFF_SR` needs *both* `clear` and `preset` (with the correct set-vs-reset-dominant precedence to match `$_DFFSR_*`), and `DFFE` needs the MUX-form `next_state : "MUX(en, d, q)"` — which is the single most fragile mapping in `dfflibmap` and version-dependent. **Fix:** rewrite §9.2 to reference `dfflegalize` for the fallback path, and for v0.1.0 default to mux-feedback enable (i.e., don't rely on DFFE Liberty mapping) rather than betting the gate-count story on it.

5. **§C2 / §10.1 — `abc -liberty` maps for area only; timing arcs are irrelevant to mapping.** Plain `abc -liberty` (as opposed to `abc9`, or `abc -constr`) does area-driven mapping and ignores `timing()` groups. So "Absent arcs silently degrade mapping quality" is false: missing tPD arcs degrade only your *C7 report*, never ABC's output. The Liberty timing data matters for `dfflibmap`'s clock/async arc inference and for the delay report, not for gate mapping. **Fix:** reword C2 — timing arcs are for reporting and for `dfflibmap` sanity, not mapping quality; if you later want delay-driven mapping you need `abc -constr <file>`, which is a different (and non-trivial) undertaking not currently planned.

6. **§7.2 — the async plan has three unstated showstoppers (this is R15, but under-specified, not merely risky).** (i) *Fan-in factoring breaks hazard-freedom:* a two-level AND-OR cover is hazard-free only as a two-level structure. With only NAND2/NOR2/AND2/OR2 (max fan-in 3), any product term with >3 literals must be factored into multiple levels, and factoring a hazard-free two-level cover into multi-level logic is *not* hazard-preserving in general (multi-level hazard-free synthesis is unsolved except in special cases). The "constrained `techmap` with a custom map file" therefore cannot simply be "map the AND-OR form structurally" — it must constrain decomposition, which is a research problem. (ii) *One-hot is incompatible with race-free assignment:* every one-hot transition changes two state bits (one clears, one sets) — a critical race by construction. §6.2's one-hot default and §7.2's "single-variable-change assignment" directly contradict; async needs a trace/STT assignment, which §7.2 doesn't address. (iii) *Espresso's default output is not hazard-free:* you need the specific hazard-free mode plus post-verification; `-Dso` (exact) does *not* guarantee hazard-freeness. The plan gestures at all of this but treats it as implementation detail. **Fix:** scope v0.1.0 async to *detection and refusal* (synthesise sync, or refuse async synthesis with a clear verdict), and treat a real async mapper as a v0.2 research task. If async must stay in v0.1.0, constrain it explicitly to ≤3-literal product terms and single-variable-change encodings, and state that limitation in the report.

7. **§10.1 / parts.csv — the second-sourcing model is wrong for S- and M-cells.** The `mfrs` column is defined as "this part number is available from multiple manufacturers," which is true for `74AUP1G00` (TI/Nexperia/Diodes all make *that* part number) but false for `TPS3839` (TI-only). The example line `SUPERVISOR,S,TPS3839,...,"TI;Diodes"` is a datasheet error and, worse, reveals the rule can't express "equivalent-but-differently-numbered alternate" (TPS3839 ↔ Diodes APX803). **Fix:** split the model into `part_suffix` (one PN) plus `equivalents` (list of alternate PNs with mfrs), and make the second-source check operate on the *set of equivalent part numbers*, not on "same PN, N mfrs."

## Significant gaps

1. **No cell simulation models (§C4 ↔ §C2).** Exhaustive simulation and mutation testing run "through the mapped netlist under Icarus," but Icarus can't read Yosys JSON, and the Liberty file C2 emits contains no Verilog. You must also emit a `cells_sim.v` of behavioural models (or use Yosys `sim`) and a `write_verilog` of the mapped netlist. This is a prerequisite of M5 that isn't listed anywhere, and it is more work than it looks (the S-cell and M-cell models must behave identically to C4's own M-cell models or you'll get false mutation results).

2. **`equiv` fallback is miscategorised (§C4).** "Where induction does not close, SymbiYosys BMC" conflates two mechanisms. sby is for the §11 *properties*; the equivalence fallback is `equiv_induct -seq N` (raise the bound), `equiv_simple` (combinational), or `equiv_induct -undef`. You *can* write an output-equality property and BMC it in sby, but that's not a drop-in "equivalence fallback" and needs its own miter. Correct the terminology and the plan or you'll burn a day discovering the API mismatch.

3. **Configurable-gate consolidation is largely illusory (§9.1, §C5).** ABC cannot see the NAND2 ↔ configurable-as-NAND2 equivalence, and it maps for area; with `area = 1.0` everywhere it has no reason to prefer the configurable cell, and C5's "deduplicate configs sharing a `part_suffix`" can only consolidate cells that are *already* the configurable type — it cannot re-map a `1G00` into a `1G57`. To actually reduce part diversity you need area biasing (weight configurable cells below dedicated gates) or a post-map cell-merge pass. Either is real work not in the plan.

4. **Refdes-stability scheme is unsound (§C6).** "Refdes derived from a hash of the logic cone" conflates a gate-level identity with a package-level refdes: two gates in one package share a refdes but have different cones, and packing decisions (which C5 is free to change) shift refdes wholesale. Also ABC re-maps cones globally, so a small edit re-optimises many cones and their hashes churn. **Fix:** stable structural cell naming (function + sorted input-cone hashes, computed topologically) → deterministic packing → refdes assigned in a stable sorted order, with the *cell→refdes* mapping recorded in the provenance map. Don't hash to the refdes directly.

5. **M-cell family/VCC inconsistency (§9.4 ↔ §10.2).** The M-cell table mixes 74HC (2–6 V) with 74LVC (1.65–5.5 V) and AUP (0.8–3.6 V). At `vcc: 1.8` (the example design.yaml) the 74HC4017/4040/74HC4017 *do not operate*; at 3.3 V the "sub-µA" static-current story degrades. This is exactly Q1/Q3 leaking into the cell list. Resolve VCC before finalising §9.4, or mark HC parts 3.3 V-only in the CSV.

6. **KiCad tie-off and S-cell representation (§C6).** Tie-offs to VCC/GND must be emitted as named *global power* references (KiCad power symbols), distinct from ordinary nets, and `no_connect` flags must be distinguished from rail tie-offs; S-cells (SUPERVISOR, OSC) carry no gate `function`, so C5/C6/C12 must special-case them (no logic cone, no SCOAP, no ABC). None of this is specified.

7. **`memory_map` check and truth-table emission (§12).** "`memory_map` … error if it fires" is fine, but use `select -assert-none t:$mem` (or `memory`'s absence) to detect it; `memory_map` itself is silent. More importantly, C1 must be pinned to emit truth tables as pure combinational `case`/`$pmux` (not `$mem`), and you should note that for n>~20 the `$pmux` tree explodes — which is the real driver behind Q4, not just simulation.

8. **R8's "two-person review" and §9.4's "hand review" assume reviewers that a personal FOSS project may not have.** There is no milestone, tool, or process backing the datasheet-transcription control that §10.1 ("nothing inferred or remembered") and §14 rely on. **Fix:** replace "two-person review" with a mechanical control — scripted cross-check of every `parts.csv` row against a pinned datasheet PDF citation, plus the golden "degenerate library must fail" and "FSM with reset+enable" tests (which you already have in §18).

## Scope recommendations

- **Defer the full async backend to v0.2.** Ship the strategy interface (M4) and *detect-and-refuse* async in v0.1.0 (a clear verdict, not a broken netlist). Async synthesis is the highest-risk, lowest-must-have-for-now component, and §7.2's gaps mean it's not deliverable at its stated milestone.
- **Trim §9.4/§9.5 to CNT4 (74LVC161/163) + SUPERVISOR + tie-off** for v0.1.0. Ripple counters (4040), the Johnson part (4017), and `DELAY` are all tied to async or 3.3 V-only and can wait. Drop `CLKBUF`/`OSC` unless a golden needs them.
- **Cut random-vector simulation entirely (§C4.3 above n=20).** It proves nothing and the coverage figure is theatre. Keep exhaustive up to a runtime cap and make formal equivalence the correctness guarantee (see Q4).
- **Ship CLI-first.** The design already gates GUI on M1–M11; further trim the app: make C13 a read-only BOM/package table (drop drag-to-regroup in v0.1.0) and make C14 a report view. The packer override is valuable but not launch-blocking.
- **Add (don't cut):** cell behavioural sim models (gap 1); the `equiv` golden-prep script (gap 2); the VCC-vs-family resolution before §9.4 finalises (gap 5).
- **Non-goals (§1.2) that are load-bearing and can't be excluded:** *timing closure* is correctly excluded, but the flop-cap / clock-fanout *viability* gates (§6, §9.6) depend on the rough cumulative-tPD model you already have in scope — that's fine, but don't treat "no STA" as "no timing model at all," or the §6 verdict becomes meaningless. And *schematic sheet generation* (§1.2) is internally contradictory: C12 renders netlistsvg schematics, which *is* generation; just reword the non-goal to "no curated/manual-quality sheet layout," not "no schematic." Everything else excluded (FMEDA, analogue, power supply design) is correctly and safely out.

## Answers to open questions

1. **VCC — make it a per-project `constraints.vcc` value, defaulting to 3.3 V for v0.1.0.** 1.8 V immediately eliminates the 74HC M-cells (min 2 V) and narrows the 125 °C second-source pool; 74AUP stays sub-µA at 3.3 V anyway, so the power story survives. Pick the authoritative tPD column per (family × VCC) at Liberty-generation time, not globally.

2. **74AUP only for v0.1.0 — but add a `family` column to `parts.csv` now.** 74LVC is a data addition, not a code change, if the schema anticipates it; shipping both families in v0.1.0 doubles the datasheet-validation and timing-model surface for marginal benefit. Ship AUP, design for LVC.

3. **Expect heavy pruning; and fix the second-source data model first.** At 125 °C and dual-source, most of §9.4/§9.5 will drop. The `TPS3839 / "TI;Diodes"` line is simply wrong — the alternate is Diodes APX803, not a second source of TPS3839 — so add `equivalents` (alternate PNs) before trusting the rule (see critical #7). Keep CNT4 (genuinely multi-sourced) and the supervisor; drop the rest for v0.1.0.

4. **Refuse to silently downgrade.** Exhaustive up to a runtime cap (roughly 2^24, ~16 M vectors, is fine under Icarus for combinational), then rely on formal equivalence alone — which is the actual proof. Random-vector simulation with a "coverage figure" is a confidence trick; offer it only as an optional smoke test explicitly labelled not-a-proof.

5. **k-induction as primary, BMC as a labelled fallback — never as "passed."** Default k = max(2 × state count, 64), overridable. When BMC is used, render it in C15 as a fourth state ("bounded pass"), not "passed," and print the bound in the report. Folding a BMC result into a green check would recreate the vacuous-pass failure you correctly fear in R2/R18.

6. **Linux (AppImage or deb) + Windows (unsigned zip/NSIS) for v0.1.0; defer macOS.** macOS notarisation and a signing cert are time and money sinks with no bearing on whether the tool is correct; a personal FOSS project shouldn't block v0.1.0 on code-signing. Document unsigned binaries clearly and add signing later.

7. **Add a dedicated async-primitive tier (C-element, SR latch) — do not hope they "fall out."** A Muller C-element is a state-holding majority gate with no two-level Boolean equivalent, so neither Espresso's cover nor ABC can produce it; it must be instantiated explicitly with a hand-reviewed behavioural model, exactly like an M-cell. "Falls out of the hazard-free cover" is false, and handshakes without C-elements will come out wrong. Fold it into the M-cell infrastructure rather than a new tier if you prefer, but it must be instantiation-only and model-reviewed.

## What the design gets right

- The sync/async split as a *strategy boundary* (M4 before M7), driven by the correct observation that ABC's redundancy removal is right for synchronous and destroys hazard-freedom for asynchronous (§7) — this is the single best architectural decision in the document.
- Verification-before-packing sequencing (M5 before M9) and the mutation suite as the anti-vacuity guard (R2, §C4.4) — the distinction between "a check exists" and "the check is wired up" is exactly right.
- The orthogonal split of equivalence vs properties (§11): equivalence proves implementation-matches-spec, properties prove spec-is-sensible, checked against the *source* so they can't pass vacuously on a degenerate result.
- The F-cell variant list itself (reset/enable/set) and the golden "FSM with reset + enable" — even though the mechanics in §9.2 need correcting, the *intuition* that missing variants inflate gate count is correct and important.
- Second-sourcing enforced in the cell library so synthesis *cannot* emit a single-sourced design (principle 4), and the `pack_cost` replacement of the "gates ÷ packages" efficiency metric (§9.7), which correctly stops punishing spare-avoidance.
- Reframing viability as a per-design *verdict* the tool emits rather than a gate on building the tool (§1.1), and the honesty of the exclusions in §13.2 (open-circuit faults "requires analysis", stuck-at is "not a safety case").
- The whole §1.2 non-goals discipline, and the "report the consequence, let the engineer decide" principle (principle 8) — the hardest thing to keep in a tool like this, and it's stated correctly throughout.
